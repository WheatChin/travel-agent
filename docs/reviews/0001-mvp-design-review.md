## Review Scope

- 产品需求：自然语言旅行需求、联网攻略、个性化逐日顺序、地图展示、地点查询、可选定位、多轮对话和隔离。
- Standards 依据：`AGENTS.md`、`CONTEXT.md`、`docs/agent-workflow.md`。
- Spec 依据：用户本次需求及设计中的已声明能力。
- 视觉依据：`ref/main-page.jpg`、`ref/list-page.jpg`、`ref/detail-page.jpg`、`ref/map-page.jpg`。
- 方法：两个独立架构审查代理分别检查 Standards 和 Spec；验证代理实际查看四张截图；主审查补充流程交叉检查及公开一手资料核验。
- 不把社交、预订、实时导航、多城优化等明确排除项自动算成缺失。

## Standards

保留独立 Standards 审查的顺序。这里检查设计是否足以落实仓库已经规定的不变量。

### S1. P1: Turn 缺少客户端基准版本契约

位置：设计 L186-191；相关承诺 L345、L455。

`TurnInput` 只有 `ownerId`、`conversationId`、`turnId` 和 `input`，没有明确 `baseVersion` 在哪里传递。后文却要求校验用户提交的基准版本。不能指望服务端加载当前版本来替代客户端真正看见的版本。

复现场景：浏览器 A 展示 v3，浏览器 B 已提交 v4；A 发送“把第二天最后一个景点删掉”。如果服务端自行把 v4 当作基准，这条原本基于 v3 的意图可能错误作用于 v4。

最小修正：定义统一的基准版本字段或命令封装；说明首次生成的空值语义；提交事务原子检查当前版本及 Run 是否仍有效。对需求尚未形成 Itinerary Version 的阶段，还应定义 Trip Brief 修订号或等价的最新 Turn 序号。

验收：过期页面的自然语言修改和 Typed Command 都被拒绝；同一基准上的并发生成只允许有效 Run 提交。

### S2. P1: Owner ID 不等于可信身份

位置：设计 L186-198、L453。

按 Owner 过滤数据的原则正确，但匿名身份的签发、验证和生命周期未定义。`ConversationEngine` 可以接收可信内部 `ownerId`，但文档必须说明它不能直接来自请求体。

复现场景：实现把客户端传入的 Owner ID 直接用于查询过滤；攻击方替换这个字段就可能绕过表面上的 Owner-scoped 查询。

最小修正：由服务端验证的匿名身份凭证派生 Owner；HTTP 请求体不允许决定身份；Conversation、Trip、Run、历史版本和进度查询均复用这一可信上下文。定义凭证失效、清除浏览器数据后的行为，以及匿名历史不能跨设备自动恢复的限制。

验收：篡改 Owner、Conversation、Trip、Run 标识不能读写他人数据；不能仅凭知道资源 ID 获得访问权。

### S3. P1: 保存状态尚不足以实现恢复运行

位置：设计 L170-177、L374、L472。

设计具体定义了等待用户输入时的保存，却没有定义活动阶段的执行恢复。SSE 重连后读取 `routing` 状态，不会自动让已经消失的执行者继续工作。

复现场景：路线结果取得后、版本提交前进程退出；重启后 Run 永久停留在 routing。另一种实现可能从头重跑，同时重置“两次修复”的上限。

最小修正：明确每阶段持久化输入输出、恢复触发者、执行租约或等价互斥机制、超时回收、持久化修复次数，以及“已提交但未发出完成事件”的恢复规则。用户补充信息应绑定待解问题或 Run，避免新 Turn 和旧 Run 的 latest-wins 规则互相抵消。

无需因此立即引入 LangGraph 或分布式队列；单进程持久化调度也可以，但必须明确承担这些职责。

验收：在外部调用前后、版本提交前后注入崩溃，均可恢复且不重复提交；断流不等于取消任务。

### S4. P2: 不可变版本引用的事实是否冻结未定义

位置：设计 L441-451；相关承诺 L20、L77。

版本 JSON、Place 缓存和 Evidence 分开保存本身没有问题，但缺少历史版本如何绑定这些事实的约束。

复现场景：Place 缓存更新坐标或名称后，打开旧版本时地图发生变化；Evidence 被覆盖后，旧版本无法还原当时为何做出安排。

最小修正：版本内冻结实际使用的事实，或引用不可变的事实修订号；历史投影不得读取可变的“最新缓存值”。晚到的路线补全也必须形成新版本，而不是悄悄改旧地图。

验收：更新 Place/Evidence 缓存后，历史版本三个投影及当时来源保持不变。

### S5. P2: Visit 时长缺少合法生产者

位置：设计 L318-324；相关限制 L254。

工作流取得的是 Leg 交通时长，校验器却还需要 Visit 游览时长；文档没有指定谁生产后者。禁止模型编造时长后，不能再默认由 compose prompt 自行填数。

最小修正：区分交通事实、建议游览时长和用户计划停留时长，定义用户指定、可信建议、版本化默认策略的优先级。缺失时使用可编辑的 Assumption，由代码计算到离时间。

这是与下方 Spec P3 相同的底层缺口，但从产品可用性角度，P3 将其评为 P1。

Standards 小结：5 项；最严重的是 S1-S3 的版本、身份和恢复契约缺口。未把 Fowler smell 当作此设计的硬性违规。

## Spec

保留独立 Spec 审查的顺序。这里检查实际旅行与对话工作流是否完整。

### P1. P1: 意图识别之后没有行为分流

位置：设计 L126-132、L243、L265-269。

设计说要识别意图，但所有自然语言输入随后都进入需求评估和生成，没有声明只读问答、解释行程、新建旅行、回答澄清和修改行程的不同路径。

复现场景：“为什么第二天去这里？”可能触发重排；“另外做一个上海两日游”可能被解释为修改当前北京 Trip。

最小修正：定义意图枚举、是否允许修改状态、目标 Trip/Run 及输出合同。建议至少区分创建、补充需求、只读问答、局部修改、全局修改、澄清回答和不支持请求；必要时允许组合意图，但必须明确顺序。

验收：问答不创建版本、不取消正在运行的规划；新旅行不覆盖原旅行。

### P2. P1: 局部修改与锁定缺少可验证语义

位置：设计 L395-402；相关验收 L584-585。

“锁定”可能表示保留地点，也可能表示保留日期、顺序、时间或全部字段；当前文档无法判定哪一种实现符合要求。

复现场景：“第二天轻松些”同时改动第一天；重生成某天覆盖了 Owner 锁定的 Visit；用户手动删除的景点在下一轮又被加回来。

最小修正：定义修改范围、锁定维度、稳定 ID 规则和范围外保持条件。明确手动删除只影响当前版本还是产生持续排除要求。对删除最后一个 Visit、缩短天数导致锁定点无处安排等情况规定拒绝、空日或澄清策略。

验收：第 2 天重排时，第 1/3 天保持不变；锁定字段不能被 repair 静默修改；扩大修改范围必须有明确依据或用户决定。

### P3. P1: 游览时长、缓冲和排程责任未闭合

位置：设计 L254、L320-324。

这是 S5 的产品侧影响：即使 Place、交通都真实，也仍可能无法生成可信时间线。09:00-18:00 连续排满景点并不自动等于“均衡节奏”。

最小修正：代码负责排程；定义游览时长来源、午餐/休息缓冲、换乘或入场缓冲、每日步行约束，以及用户调整的优先级。不做餐厅推荐不等于不留吃饭时间。

还应说明首末日可用时段和可选起终点。酒店搜索/预订可以不做，但用户给出酒店地址时是否可作为起点需要有答案。未提供起点时明确“从首个景点开始计时”，不要暗示已经包含所有交通。

验收：仅给出“北京三天，人文为主”也能使用透明默认值形成可执行的计划；补充下午抵达后，第 1 天按缩短窗口重新验证。

### P4. P2: 最低旅游事实清单缺少入场限制

位置：设计 L323-339。

已覆盖开放时间和引用，但没有要求取得预约要求、最晚入场、入场条件及其对应日期。

复现场景：Evidence 已写明需要预约或提前停止入场，计划仍只根据闭馆时间计算“能游览完”。

最小修正：规定最小研究字段，已知限制参与排程和详情展示；未核实项告警；Owner 明确要求已核实入场可行时，不能仅靠 Warning 通过。预约提示不等于代订，也不等于保证有库存。

验收：已知不能满足的入场硬条件不能提交为可行行程；未知项不能显示为已确认。

### P5. P2: 单城市范围未落到供应商覆盖和区域规则

位置：设计 L27、L87、L307。

“一个城市”没有说明首发支持范围、城市标识及远郊景点的判断方法。

复现场景：超出适配器覆盖的目的地通过需求门后才失败；市中心距离较远的景点被错误认定为“不在目的地区域”。

最小修正：声明首发覆盖范围、城市规范标识和周边区域规则；在需求门一次性返回不支持项。不要用简单的中心点半径代替未经讨论的产品边界。

Spec 小结：5 项；最严重的是 P1-P3 的对话分流、修改保持与真实排程。与 Standards 的时长项重叠，不应把这 10 条视为 10 个完全独立的问题。

## Cross-Checks

以下为主审查的补充，不混入两个独立轴线重新排序。

### C1. P1: 总流程与 Typed Command 契约文字不一致

位置：设计 L123-138 对比 L390-402。

总流程把命令执行后统一送入搜索、LLM 编排和 LLM 修复；后文要求命令只在语义选择或再生成确有必要时使用模型。按图实现，会让“删除一个点”或“取消 Run”意外启动整套规划。

修正方向：入口先分发控制命令、只读问答、确定性行程修改、语义修改和生成。明确校验失败的手动修改是拒绝并展示问题，还是经过授权后启动语义修复；不得自动扩大行为。

### C2. P1: degraded 边界可能与硬约束相冲突

位置：设计 L162、L287-288、L321、L331-332。

文档允许外部事实缺失时 degraded，但未区分“没有几何形状”“没有耗时”和“已确认不可达”。缺少交通耗时时，校验器无法证明一天装得下；已确认不可达则不是一般未知事实。

修正方向：定义路线事实完整度和允许提交的矩阵。只有 geometry 缺失时可以保留已确认耗时并不画道路；耗时缺失时要明确未验证时间可行性，或者按用户硬要求阻塞；已知违反硬约束不得 degraded 绕过。`ERROR` 禁止所有正式版本提交，而不只是禁止标成 completed。

### C3. P2: 有 Evidence ID 不等于引用支撑了断言

位置：设计 L205、L249、L334-339。

当前只命名了 Travel Research 和 Evidence，没有明确“搜索词 -> 搜索/抓取 -> 文档去重 -> 字段抽取 -> POI 绑定 -> 来源冲突处理”的责任。纯确定性校验器也不能只靠一个存在的 Evidence ID 判断任意自然语言陈述得到原文支持。

修正方向：建立字段级事实记录，至少包含 Place 绑定、属性、值、来源片段、检索时间、适用日期和冲突/未知状态；代码检查关联与时效，LLM可在受约束任务中辅助抽取。时间、预约等关键字段不从自由文案反解析。来源未覆盖时显示未知，不为凑引用绑定无关页面。

来源优先级、缓存时效、单次检索预算、候选不足时是否补搜都应写成策略。不需要为搜索新增 runtime subagent。

### C4. P2: Prompt 调优只有指标清单，没有迭代闭环

位置：设计 L263-281、L567-576。

独立 prompt 版本化方向正确，但还没有可重复实验协议。无法据此判断一次 prompt 修改是否真正改善了“人文偏好”，还是只提高了 schema 通过率。

修正方向：每个任务定义输入、输出、允许字段、拒绝/空输出行为、token 与重试预算及少量正反例。先固定模型、工具 fixture 和测试集，按失败类型修改 prompt，再用独立回归集比较；硬约束/ID 合法性由代码判定，偏好和解释质量采用清晰量表及人工抽检。

建议最小测试集包括：只读问答、纠正前文、模糊地点、无日期、首日半天、仅改一天、保留锁定项、搜索不足、工具失败、恶意网页指令。可复现记录还需要工具 fixture/事实修订和排程策略版本，而不只是 promptVersion。

### C5. P2: Key 类型被写成了未经确认的事实

位置：设计 L423、L591-592。

本次用户只给了 Key 字符串及预期功能，没有提供控制台平台类型。仅凭字符串无法在本次审查中确认“这就是 Web Key”。

修正方向：将 L423 改为“凭证平台类型待控制台确认”；分别列出前端渲染、后端 POI/路线的能力配置和验证步骤。本次没有使用该 Key 发出 API 调用，也没有把它写入报告或搜索请求。

另需防止 L244 中的 “accessibility needs” 被统一当作软偏好：例如用户明确表示不能走楼梯，应保留为 Hard Constraint；无法核实无障碍路线时不能声称已满足。此处应补分类示例，而不是新增一套无障碍专家 Agent。

## Architecture Judgment

建议保留目前的模块化单体、显式工作流、单一版本多视图、模型适合语义任务而代码负责提交/校验的方向。现阶段的关键不足是输入输出和状态契约，而不是缺少 runtime specialist agents。

建议的职责分配，仅供下一版设计讨论，尚未批准：

| 环节 | LLM | 确定性代码 |
| --- | --- | --- |
| 入口分流 | 解释自然语言意图、抽取需求 patch | 身份、幂等、版本与意图允许操作 |
| 需求评估 | 辅助识别表述歧义 | 聚合阻塞项、保留硬约束、应用可见默认值 |
| 研究与候选 | 生成受约束搜索词、抽取事实、语义排序 | 请求执行、预算、去重、来源与 Place 绑定校验 |
| 行程编排 | 在 supplied IDs 内选择、分组、建议顺序 | 路线请求、时长策略、时间轴计算、约束检查 |
| 行程修改 | 把语言变更映射到目标范围和稳定 IDs | 应用 patch、锁定/范围保持、重算受影响 Legs |
| 输出与提交 | 根据受支持事实解释推荐理由 | 验证、原子提交、快照投影、SSE 状态 |

不要只在排好后判断“时间够不够”，也应给编排提供适量的地理/交通依据及可比较目标。没有必要在 MVP 强行实现全局最优算法，但应能识别明显绕路，并明确候选数量、路线调用预算和有限优化策略。这是设计建议，不是已观察到的实现错误。

## AGENTS.md Judgment

现有 `AGENTS.md` 适合作为开发代理的项目规则入口，已经包含来源、不变量和角色路由。它不是面向旅行用户的运行时 system prompt，不应直接把整个文件送给旅行模型。

下一版应继续让运行时 prompt 随任务版本化，并由代码注入候选、事实和允许修改范围。应用骨架确定后，再在开发说明中补真实的启动/测试命令、目录职责、迁移流程及验收入口；当前尚无脚手架，不应杜撰这些命令。

## Primary Sources Checked

本次通用 web 搜索工具没有返回可读结果，改用浏览器实际打开下列一手页面。以下只支撑架构原则，不证明问旅采用相同方案，也不是选定任何 SDK 的决定。

1. [Anthropic: Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
   - 核验内容：预定义代码路径的 workflow 与模型动态控制的 agent 的区别；routing、prompt chaining 和迭代评价。
   - 本报告推论：本项目可保留显式工作流，优先补意图分流和受控修复，不必把每一步拆成 Agent。
   - 原文发表于 2024-12-19，页面提示工具生态已变化；本报告只使用其架构原则，不据此推荐旧工具版本。
2. [LangGraph 官方 GitHub 仓库](https://github.com/langchain-ai/langgraph)
   - 核验内容：其定位为长运行、有状态工作流/Agent 的底层编排基础设施，提供持久执行、人机交互和状态能力。
   - 本报告推论：是否采用该库是工程取舍，但选择不用不能省略自己承诺的恢复合同。
3. [LangGraph: Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
   - 核验内容：thread-scoped checkpointer 与跨 thread store 的区别；内存持久化不能跨进程重启保留状态。
   - 本次从仓库中的 durable-execution 链接访问后落到该 Persistence 页面，因此未声称核验了旧路径中的全部逐节点重放细节。
4. [OpenAI: Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
   - 核验内容：schema 约束不消除语义错误；不相关输入需要定义处理方式；拒绝和不完整输出需要显式处理。
   - 本报告推论：strict JSON Schema 不能替代旅游事实与跨记录约束校验，也不能替代只读问答分支。

## Proposed Review Gate

不建议直接以现文冻结所有实现合同。下一步先修订设计中的四组内容，再按现有开发流程提交编码：

1. Turn、身份、版本、意图分流和局部修改合同。
2. 旅游事实、时长策略、排程、硬约束及降级矩阵。
3. Run 持久执行、恢复、取消/替代、提交与重连语义。
4. 前端页面/抽屉联动、可复现 prompt 评估及端到端失败场景。

框架、单城/七天、匿名身份、PWA 和不做预订属于应确认的产品/工程选择，并非用户原始三项功能自然推出的唯一答案。建议保留合理缩限，但将“已确认决定”与“本次仍待确认的假设”写清楚。
